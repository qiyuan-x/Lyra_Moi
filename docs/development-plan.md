## 1. 执行原则

- 按完全重构实施，不兼容现有业务代码和数据库。
- 每个阶段先完成契约和测试，再接入界面。
- 默认使用假供应商完成自动测试，真实 API 测试单独运行。
- 每阶段结束必须通过类型检查、单元测试、集成测试和构建。
- 重建前清理旧缓存和构建产物。
- Git 只提交源码、迁移、测试、文档和必要资源。
- 类型、函数、文件名和注释使用简单明确的名称，不使用无实际含义的包装词。

## 3. 任务拆分

### M0：建立干净源码基线

#### M0-1 清理现有架构

工作：

- 现有 `apps/server`、现有前端业务、Pi Agent 集成和旧数据库实现不进入新架构。
- AnythingLLM 下载副本作为 Agent 源码调研和提取来源，但完整副本不进入 Git。
- 只提交经过改造、实际使用的 AIbitat 源码，并保留 MIT 许可证和归属说明。
- 删除构建文件、缓存、旧运行数据和源码目录中的依赖目录。
- 保留已审核设计文档。

验收：

- 仓库中源码、测试、构建、部署和运行数据边界清楚。
- `git status` 不包含 `node_modules`、`dist`、`data` 内容和 AnythingLLM 副本。
- 不执行旧数据库迁移。

#### M0-2 创建新工作区

创建：

```text
apps/web
apps/api
apps/worker
apps/launcher
packages/contracts
packages/core
packages/agent-engine
packages/agent-tools
packages/providers
packages/storage
resources/prompts
tests/unit
tests/integration
tests/e2e
tests/fixtures
```

验收：

- 根目录构建、检查、测试和清理命令可运行。
- 各包职责单一，不循环依赖。

### M0A：Agent 与统一生成服务技术验证

在全面实现数据库和 UI 前，先完成最小纵向验证，避免后期才发现 AIbitat 无法满足持久化工具流程。

#### M0A-1 提取 AIbitat 最小核心

实现：

- 从 AnythingLLM 提取工具注册、同步/流式工具循环、工具结果回传和取消机制。
- 移除 Workspace、SystemSettings、Telemetry、RAG、默认 Skills 和 AnythingLLM WebSocket 依赖。
- 建立 `AgentEngine`、`LlmProvider`、`ToolRegistry`、`AgentEventSink` 接口。
- 使用假 LLM Provider 测试，不调用真实 API。

验收：

- 假 LLM 可以先返回工具调用，收到工具结果后再返回最终文字。
- 工具参数通过 JSON Schema 校验。
- 最大工具调用次数和取消生效。
- Agent Engine 不依赖 Web、API、SQLite 具体实现。

#### M0A-2 统一 GenerationService 验证

实现最小内存版本：

```text
手动调用 -> GenerationService -> FakeImageProvider
Agent工具 -> GenerationService -> FakeImageProvider
```

验收：

- 两个入口产生相同的标准生成请求和输出结构。
- 有序素材标签在两个入口中完全一致。
- 生成逻辑没有复制。

#### M0A-3 暂停和恢复验证

实现最小 Agent 检查点：

```text
tool_call 已保存
-> Agent waiting_tool
-> 图片工具完成
-> tool_result 已保存
-> Agent resuming
-> 最终回复
```

验收：

- Agent 等待图片时不占用 HTTP 请求。
- 模拟 Worker 重启后不会重复创建图片任务。
- 浏览器连接不存在时流程仍可完成。

### M1：核心契约、数据库和运行目录

#### M1-1 公共契约

实现：

- ID、分页、错误响应、素材、消息、Agent Run、Agent Step、任务、供应商和 SSE 类型。
- 运行时请求校验 Schema。
- 前后端共用契约，不复制类型。

验收：

- 错误请求得到稳定错误码。
- 契约包不依赖 Web、API 或 Worker。

#### M1-2 运行目录

实现：

- 开发模式使用仓库 `data`。
- 打包模式使用 `sys.executable` 同级 `data`。
- 服务器模式使用 `LYRA_DATA_DIR`。
- 创建 config、database、blobs、thumbnails、logs、temp、run 子目录。

验收：

- 自动测试确认所有运行文件只出现在指定数据目录。
- 不向用户目录、源码目录其他位置和系统临时目录持久化业务数据。

#### M1-3 SQLite 迁移和仓储

实现 `docs/data-model.md` 中的首版迁移、事务和仓储接口。

验收：

- 新数据库可以从零创建。
- 重复执行迁移不会破坏数据。
- WAL、外键约束和忙等待参数正确启用。
- API 和 Worker 发现迁移版本不一致时拒绝运行并记录明确日志。

### M2：供应商与设置

#### M2-1 供应商注册中心

实现：

- `openai`、`gemini`、`openai-compatible` 三种协议类型。
- 一个连接下配置多个 LLM、图片和预留建模模型。
- 默认 LLM 和默认图片模型。
- 相同协议允许多个连接。

验收：

- 新增、修改、停用和软删除连接正常。
- 模型名称不写死在源码。
- 本地 URL 可以保存和测试。

#### M2-2 密钥存储

实现：

- 设置 API 接收密钥并原子写入 `data/config/.env`。
- 数据库只保存环境变量名称。
- GET 接口只返回 `hasApiKey` 和掩码。
- 日志和错误信息自动清除密钥。

验收：

- 前端网络响应中找不到 API Key 原值。
- 更新非密钥字段不会清除现有密钥。
- 显式清除密钥功能正常。

#### M2-3 连接测试和模型发现

实现：

- 连接测试。
- 支持时发现模型列表。
- 不支持发现时允许手动添加模型。

验收：

- 测试失败返回可理解错误，不泄漏请求头。
- 远端不可用不会影响应用启动。

### M3：素材系统

#### M3-1 素材上传和存储

#### M3-2 缩略图和素材查询

实现：

验收：

- 大图不直接用于素材列表缩略展示。
- 删除素材不会破坏历史任务记录。

### M4：持久化任务与 Worker

状态：已完成。

#### M4-1 SQLite 执行队列

实现：

- Agent Run 与图片 Job 分开原子领取、锁定、完成、失败和取消。
- Agent `waiting_tool` 和 `awaiting_user` 不占用 Worker。
- `image.generate` 和预留 `model.generate` 长任务。
- Worker 心跳和版本检查。

验收：

- 两个 Worker 竞争时同一任务只执行一次。
- 进程退出后运行中任务标记为 `interrupted`。
- 重试创建新任务，不覆盖历史。
- Agent 恢复不会重复执行已经完成的工具步骤。

#### M4-2 任务事件和 SSE

实现：

- Worker 写入批量事件。
- API 通过 SSE 转发。
- `Last-Event-ID` 断线续传。
- 前端重连后通过 REST 校正最终状态。

验收：

- 刷新页面后生成任务仍可恢复。
- SSE 断开不会取消后端任务。
- 事件不包含密钥和绝对路径。

#### M4-3 假图片供应商

实现测试用 Provider：延时后从 fixtures 返回图片，支持成功、失败、超时和取消场景。

验收：

- 不调用真实 API 即可完成全部任务和 UI 自动测试。

### M5：AIbitat Agent Engine

状态：已完成。

#### M5-1 AIbitat 生产化改造

实现：

- 将 M0A 验证代码整理为正式 `packages/agent-engine`。
- 文本对话历史。
- 有序附件标签和素材元数据。
- 结构化工具调用校验。
- 纯文字回复。
- 一次或多次 `generate_image` 调用。
- `request_user_input` 和恢复执行。
- Agent Run、Agent Step 和流式事件持久化。

不实现：

- 图片内容分析
- 固定自然语言意图枚举
- Agent 直接访问文件系统或数据库
- AnythingLLM Workspace、RAG 和前端协议

验收：

- “把图二人物替换为图一”能保持附件顺序创建图片任务。
- 任意未预设图片要求仍走通用工具。
- 非生成对话不会错误创建图片任务。
- 非法工具参数被拒绝并记录可理解错误。
- 图片任务完成后 Agent 可以从工具结果继续生成最终回复。
- Agent 请求补充信息后可以由用户恢复。

#### M5-2 原始输入和执行快照

实现：

- 原样保存用户消息。
- 保存 Agent 最终提示词。
- 保存附件、供应商、模型和清理后的参数快照。

验收：

- 任务详情可以复现请求。
- Agent 改写不会覆盖用户原始文本。

11. 用户验收结果并继续对话修改。

13. 确认两种模式的结果都进入同一素材库。
14. 停止服务并确认进程全部退出。
15. 确认只有 EXE 同级 `data` 产生运行数据。

## 4. 建议实施顺序

先完成 M0 和 M0A，验证 AIbitat 改造、持久化等待和统一 GenerationService。验证通过后完成 M1 至 M4 的正式基础设施；再完成 M5 至 M8 的核心产品；最后完成 M9 至 M11 的本地启动、服务器部署和发布。

不要在任务队列、素材存储和供应商注册中心完成前开始堆叠完整 UI，否则会再次形成前端状态代替后端事实数据的问题。

## 5. 第一阶段完成标准

满足以下条件才算首个可用版本：

- 用户可以配置多个 OpenAI、Gemini 和 OpenAI Compatible 连接及模型。
- 用户可以上传图片并显式添加到发送框。
- 图片生成提供 Agent 和手动两种可切换模式。
- 改造后的 AIbitat Agent 可以对话、调用 `generate_image`、等待工具和恢复执行。
- 手动模式可以绕过 Agent 直接生成。
- 两种模式使用同一个 GenerationService、任务队列和素材库。
- 图片任务在独立 Worker 中运行。
- 生成状态在工作区和任务抽屉中实时显示并可恢复。
- 输出自动成为素材，可点击后继续作为输入。
- 提示词模板只插入文字，不限制自然语言。
- Windows 启动器可以稳定管理服务并打开浏览器。
- 同一构建结果可以部署到单用户服务器。
- API Key、SQLite 和素材文件不被前端或静态目录暴露。
